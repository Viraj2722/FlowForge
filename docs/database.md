# Database Design & the JDBC-vs-JPA Split

This document explains **why** the schema looks the way it does — the kind of reasoning
an interviewer will probe.

## Who owns the schema? Flyway, not Hibernate

Migrations under `src/main/resources/db/migration` are the single source of truth.
Spring Boot runs them at startup. In Phase 3, Hibernate is set to `ddl-auto=validate`,
so it checks its entity mappings against this schema but **never changes it**.

**Why not `ddl-auto=update`/`create`?** Auto-DDL is convenient in a toy app and dangerous
in a real one: it can silently drop columns, can't express data migrations, isn't
reviewable in a PR, and gives no rollback story. Versioned migrations are reproducible
and auditable. This is the single most important persistence decision in the project.

## Conventions (applied uniformly)

| Concern | Choice | Why |
|---|---|---|
| Primary keys | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | SQL-standard identity; maps to JPA `@GeneratedValue(IDENTITY)` |
| Timestamps | `TIMESTAMPTZ`, default `now()` | store UTC instants, not naive local times |
| Enums | `VARCHAR` + `CHECK` | portable, easy to add values, maps to `@Enumerated(STRING)`; native PG `ENUM` is painful to evolve |
| Flexible config/payload | `JSONB` | typed, indexable JSON for step params, task output, audit diffs |
| Concurrency | `version INTEGER` on mutable roots | drives JPA optimistic locking (`@Version`) in Phase 5 |

## Tables — and the ones we intentionally did NOT create

Created: `roles`, `users`, `user_roles`, `workflows`, `workflow_steps`,
`step_dependencies`, `workflow_executions`, `task_executions`, `dead_letter_tasks`,
`audit_logs`.

- **No separate `tasks` table.** Every `workflow_step` *is* one task of a `task_type`. A
  second table would duplicate the step 1:1 for no benefit.
- **No separate `retry_queue` table.** Retry state (`attempt`, `max_attempts`,
  `next_retry_at`, `last_error`) lives as columns on `task_executions`. The scheduler
  polls `WHERE status='RETRYABLE_FAILURE' AND next_retry_at <= now()`, backed by the
  composite index `idx_task_exec_retry`. A queue table would just mirror this row.
- **We DID create `dead_letter_tasks`.** Dead letters have a different lifecycle (manual
  inspection + replay) and retention, and we want to query them without scanning the hot
  `task_executions` table. That justifies a dedicated table.

## Relationships (preview of the JPA mapping in Phase 3)

- `workflows` 1—* `workflow_steps` (one-to-many, cascade delete)
- `workflow_steps` *—* `workflow_steps` via `step_dependencies` (self many-to-many DAG)
- `workflows` 1—* `workflow_executions`
- `workflow_executions` 1—* `task_executions`
- `users` *—* `roles` via `user_roles`
- `task_executions` 1—1 `dead_letter_tasks` (optional)

## Why JDBC for reporting, JPA for domain writes

| Operation | Tech | Reason |
|---|---|---|
| Create workflow + steps; update execution/task state | JPA/Hibernate (Phase 3+) | identity, cascades, dirty checking, optimistic locking earn their keep on writes |
| Dashboard counters, per-workflow throughput, failure breakdowns | **JDBC** (`ReportingJdbcDao`) | `GROUP BY`/`JOIN` projections with no entity to hydrate; let the DB aggregate and return flat rows |

This "ORM for writes, SQL for read models" split is a lightweight form of **CQRS** and is
common in production systems. It's a deliberate choice, documented so it can be defended
— not JDBC and JPA sprinkled at random.

`ReportingJdbcDao` uses Spring's `JdbcTemplate`, which manages the `Connection` /
`PreparedStatement` / `ResultSet` lifecycle (always closed, even on error), binds
parameters safely (no SQL injection), maps rows via `RowMapper`, and translates
`SQLException` into Spring's unchecked `DataAccessException`.
